## 1. Overview

The QuickJS GCC JIT is a tier-2 compiler that translates hot JavaScript bytecode
functions into native x86-64 machine code via GCC.  The design is:

```
JS source
    │
    ▼ (parser + bytecode compiler, quickjs.c)
bytecode (JSFunctionBytecode)
    │
    ├── interpreter  (immediate execution, always available)
    │
    └── JIT tier-2  (when call count ≥ JIT_THRESHOLD_GCC)
            │
            ▼
        C source (generated by quickjs-jit.c)
            │
            ▼ gcc -O2/-O3 -flto -shared -fPIC
            │
            ▼
        .so (dlopen'd; jit_func pointer patched atomically)
            │
            ▼
        native x86-64 (called directly on every subsequent invocation)
```

The interpreter and JIT coexist: a function starts in the interpreter, crosses the
call-count threshold, gets compiled by GCC in a background thread, and subsequent
calls transparently invoke the native version.

## 2. Architecture

### 2.1 Components

| File | Role |
|---|---|
| `quickjs.c` | Bytecode interpreter; JIT hot-path probe (§18055); IC helpers |
| `quickjs-jit.c` | Code generator, cache manager, GCC driver, IC check macro |
| `quickjs-jit.h` | Public JIT API; `JSJITICEntry`; `JIT_IC_CHECK` macro |
| `qjs.c` | CLI wiring for `--jit-aot`, `--jit-warmup`, `--jit-link`, `--jit-dump-c`, `--jit-threshold-gcc`, `--jit-save-sources` |
| `quickjs-libc.c` | `js_loadScript` AOT hook: installs combined.so for `load()`'d files |

### 2.2 Hot-path probe

Every `JS_CallInternal` entry checks, for eligible functions:

```c
JSJITFunc jf = __atomic_load_n(&b->jit_func, __ATOMIC_ACQUIRE);
if (unlikely(jf != NULL)) {
    return jf(ctx, this_obj, argc, argv, b->cpool, var_refs);
}
if (!b->jit_no_compile) {
    int thr = js_jit_get_threshold();  /* runtime override via --jit-threshold-gcc */
    if (thr >= 1 && ++b->jit_call_count == thr)
        js_jit_queue_gcc(ctx, b, var_refs);
}
```

The `jit_func` pointer is written with `__ATOMIC_RELEASE` after GCC finishes, so
the acquire load above sees a consistent state with no locks.

### 2.3 JIT function signature

Every compiled function has the C signature:

```c
JSValue __jit_f_<hash>(JSContext *ctx,
                       JSValue    this_obj,
                       int        argc,
                       JSValue   *argv,    /* caller's argument array */
                       JSValue   *cpool,   /* function's constant pool */
                       JSClosureVar **var_refs);
```

The `<hash>` is a 64-bit FNV-1a hash of the function's bytecode, used as the
stable key for all cache files.

### 2.4 Background compilation

`js_jit_queue_gcc` submits the function to a POSIX thread pool (default: one
worker thread).  GCC compilation is synchronous inside the worker: `fork()` +
`exec("gcc ...")` + `waitpid`.  The resulting `.so` is opened with `dlopen` and the
symbol resolved with `dlsym`.  The `jit_func` pointer is then patched atomically.
The interpreter continues running the function until the patch is visible.

## 3. Build System

### 3.1 Enabling the JIT

```sh
make CONFIG_JIT=y
```

All normal build targets work with `CONFIG_JIT=y`:

```sh
make CONFIG_JIT=y             # build qjs, qjsc, libquickjs.a
make CONFIG_JIT=y qjs-debug   # debug build
make CONFIG_JIT=y test        # run test suite
make CONFIG_JIT=y CONFIG_ASAN=y qjs   # AddressSanitizer build
```

### 3.2 Makefile variables

| Variable | Default | Description |
|---|---|---|
| `CONFIG_JIT=y` | (off) | Compile in the GCC JIT tier |
| `JIT_THRESHOLD_GCC` | `100` | Default call count before GCC compilation fires (overridable at runtime with `--jit-threshold-gcc=N`) |
| `JIT_INCLUDE_DIR` | `$(pwd)` | `-I` path for JIT-generated C files (must contain `quickjs-jit.h`) |

Example — low threshold for testing:

```sh
make CONFIG_JIT=y JIT_THRESHOLD_GCC=2 qjs   # compile-time default
./qjs --jit-threshold-gcc=2 script.js        # runtime override (no rebuild needed)
```

### 3.3 What `CONFIG_JIT=y` adds

- Compiles `quickjs-jit.c` and links it in.
- Adds the hot-path probe block in `JS_CallInternal`.
- Links `-ldl` and `-lpthread`.
- Defines `DCONFIG_JIT`, `DJIT_THRESHOLD_GCC=N`, `DJIT_INCLUDE_DIR=<path>`.

The interpreter is otherwise unchanged; interpreter performance is unaffected when
no JIT function has been installed.

## 4. CLI Flags

All flags are only available when `qjs` is built with `CONFIG_JIT=y`.

### `--jit-aot`

**AOT (ahead-of-time) mode.**  Before executing the script, compile every eligible
function that appears in the loaded bytecode tree using GCC.  Execution starts only
after all GCC jobs finish (via `js_jit_drain()`).

If `combined.so` exists in the cache, it is preloaded first (`js_jit_preload_combined`)
and functions found in its manifest are installed directly without spawning GCC.

Implies the cache is enabled; `~/.cache/qjs-jit/` is created if absent.

### `--jit-warmup`

**Warmup mode.**  Identical to `--jit-aot` during execution (compile everything,
install from combined.so if present, drain GCC), but exits after the script
completes rather than continuing a REPL loop.  The primary purpose is to populate
the cache for a subsequent `--jit-link` run.

After a `--jit-warmup` run, every eligible function in the script has a
`<hash>.so` and a `<hash>.c` file in the cache.

### `--jit-link`

**Link mode.**  After normal execution, combines all `.c` files seen during this
run into `~/.cache/qjs-jit/combined.so` using GCC with `-O3 -flto -shared`.

On the first invocation, also compiles `quickjs.c` to an LTO fat-binary object
(cached by source mtime as `qjs_ic_<mtime>.o`) and includes it in the link command
for additional cross-module optimization.

Implies `--jit-aot` (execution happens before linking).

GCC output is logged to `/tmp/qjs_jit_link.log` on failure.

### `--jit-dump-c`

Print the generated C source of every function that passes through the JIT code
generator to `stderr`, with a header comment:

```c
/* ==== JIT: <function-name> [<hash>] ==== */
```

Useful for inspecting what code the generator produces and for debugging unsupported
opcodes.

### `--jit-threshold-gcc=N`

**Runtime threshold override.**  Sets the number of calls before a function is
enqueued for GCC compilation, overriding the compile-time `JIT_THRESHOLD_GCC`
constant (default 100).  No rebuild required.

| Value | Behaviour |
|---|---|
| `N >= 1` | Compile after N calls.  `N=1` means JIT kicks in from the second call onward. |
| `N = 0` | AOT pre-pass: all statically-visible functions are compiled before execution starts (same as `--jit-aot` but without requiring a prior `--jit-warmup`). Dynamic closures created at runtime use the counter path with threshold disabled — they run interpreted. |

```sh
./qjs --jit-threshold-gcc=1  script.js   # JIT from first call
./qjs --jit-threshold-gcc=10 script.js   # faster warm-up for short scripts
./qjs --jit-threshold-gcc=0  script.js   # AOT pre-pass, then continue running
```

The threshold is stored in `jit_threshold_gcc` (in `quickjs-jit.c`), accessed via
`js_jit_get_threshold()` / `js_jit_set_threshold()`.

### `--jit-save-sources`

**Save original JS source alongside compiled artifacts.**  For each JIT-compiled
function, writes the original JavaScript source text to `<cache>/<hash>.js`
next to the existing `<hash>.c` and `<hash>.so`.

```sh
./qjs --jit-save-sources script.js
ls ~/.cache/qjs-jit/
# 05230537aa4ad0b0.js   ← original JS source of the function
# 05230537aa4ad0b0.c    ← generated C source
# 05230537aa4ad0b0.so   ← compiled native library
```

Source text comes from `b->debug.source` (set by the parser).  **No-op if the
script is run with `-s` / `--strip-source`** — stripped bytecode has no debug info.
Files that already exist in the cache are not overwritten.

Useful for:
- **Debugging** — immediately see which JS function produced a given `.so` without
  searching the original script.
- **Self-documenting cache** — the cache directory becomes a complete record of
  what was compiled and what native code it produced.
- **Tooling** — scripts correlating hash → function name → source can read `.js`
  directly instead of parsing the `/* JS function: name */` comment in `.c`.

## 5. Execution Modes

### 5.1 On-demand JIT (default)

```sh
./qjs script.js
```

Functions are compiled in the background as the call count threshold is crossed.
If a cached `.so` exists for the function's hash, it is loaded immediately instead
of re-compiling.  The script runs normally; the JIT accelerates subsequent calls
to the same function.

### 5.2 AOT mode

```sh
./qjs --jit-aot script.js
```

The entire bytecode tree (all loaded functions, including those reached via
`load()`) is compiled before execution.  Execution then runs with all JIT
functions pre-installed.

If `combined.so` is present in the cache, functions are installed from it in bulk
rather than loading individual `.so` files.  This is the recommended mode for
repeated execution of the same script.

### 5.3 Three-step workflow (best performance)

This workflow produces a single optimised shared library containing all JIT
functions, compiled together with GCC's inter-procedural optimisation:

```sh
# 1. Warm the cache (execute once; compile + save .c for every function)
./qjs --jit-warmup script.js

# 2. Link (LTO-combine all .c files into combined.so with -O3)
./qjs --jit-link script.js

# 3. Execute (install from combined.so; no GCC during the run)
./qjs --jit-aot script.js
```

After step 2, `combined.so` contains all JIT functions compiled together.  GCC can
inline across function boundaries, apply constant propagation, and vectorise loops
that span multiple functions.

Step 2 also adds `quickjs.c` to the GCC invocation as an LTO object, enabling the
compiler to see the implementation of internal helpers and optimise call sites into
them.

## 6. Cache Layout

The cache lives at `~/.cache/qjs-jit/` by default.  Override with:

```sh
QJS_JIT_CACHE=/path/to/dir ./qjs ...
```

### File types

| Pattern | Description |
|---|---|
| `<hash>.js` | Original JS source of the function (only with `--jit-save-sources`) |
| `<hash>.c` | Generated C source for the function |
| `<hash>.so` | Individually compiled shared object |
| `<hash>.skip` | Empty marker: function has unsupported opcodes; skip permanently |
| `combined.so` | LTO-combined library produced by `--jit-link` |
| `qjs_ic_<mtime>.o` | LTO fat-binary of `quickjs.c`, cached by source mtime |

`<hash>` is a 16-digit lowercase hex string (64-bit FNV-1a of the bytecode).

### Cache invalidation

The cache is keyed by bytecode hash.  If the script changes in a way that alters
any function's bytecode, the old `.so` is simply not found and GCC recompiles.
Old files are not automatically deleted; run `rm -rf ~/.cache/qjs-jit/` to clear.

The `qjs_ic_<mtime>.o` LTO helper is invalidated automatically when `quickjs.c` is
modified (the mtime changes, producing a new filename and leaving the old one
stale — delete manually if disk space is a concern).

## 7. Code Generation

### 7.1 Structure of generated code

For a bytecode function `f`, the generator emits a C file with roughly this shape:

```c
#include "quickjs-jit.h"
#define _RT  (&js_jit_rt)

JSValue __jit_f_<hash>(JSContext *ctx, JSValue _this,
                       int _argc, JSValue *_argv,
                       JSValue *_cpool, JSClosureVar **_var_refs)
{
    /* typed locals (Phase 8.1): int/double for stable-type variables */
    int    _li0, _li1;          /* integer locals */
    double _ld0;                /* float64 local */
    JSValue _tsv0, _tsv1, ...;  /* JSValue stack slots */
    int _sp = 0;                /* virtual stack pointer */

    /* IC entries for property accesses (Phase 6.2) */
    static JSJITICEntry _ic42 = {NULL, 0};

    /* function body — one C block per bytecode instruction */
    ...
_ex:
    /* exception unwind: free any live JSValue stack slots */
    ...
    return JS_EXCEPTION;
}
```

### 7.2 Stack model

The interpreter's operand stack is modelled as an array of `JSValue` named `_tsv0`,
`_tsv1`, …, indexed by a compile-time stack depth counter `d`.  The generator tracks
the depth statically for all straight-line code; merge points at backward jumps
reset the depth conservatively.

Typed locals (integer or float64) are separate C `int` / `double` variables.  The
generator promotes a slot to a typed local when it detects a run of integer
operations (Phase 8.1), and boxes it back to a `JSValue` when the value is passed to
a generic slow path.

### 7.3 Exception model

Every call that can throw returns a JSValue; the generated code checks for
`JS_EXCEPTION` with the `_CHK(v)` macro and jumps to `_ex:` on failure.  At `_ex:`,
all live `JSValue` stack slots are freed.

### 7.4 Unsupported opcodes

If the generator encounters a bytecode opcode it has not implemented, it logs:

```
[JIT] gen_body: unhandled opcode 0xNN at pc=K
```

and writes a `.skip` file for the function's hash.  The function is never compiled
again in that cache; it always runs in the interpreter.

## 8. Optimisation Passes

The generator applies the following optimisations, in roughly the order they were
introduced:

### Phase 5 — Typed variables (integer fast-paths)

Integer arithmetic (`+`, `-`, `*`, comparisons) that stays within 32-bit int bounds
is emitted as direct C integer operations.  The generated code checks the tag of
each operand; if both are `JS_TAG_INT`, a fast integer path is taken; otherwise the
vtable slow path (`_RT->add`, etc.) is called.

Result: eliminates boxing/unboxing for integer-only loops.

### Phase 6.2 — Inline Property Cache (IC)

`get_field`, `get_field2`, and `put_field` opcodes emit a monomorphic inline cache
check (see §9 below) before falling back to the full property lookup.

### Phase 7 — GCC disk cache

Compiled `.so` files are cached to disk and reloaded on subsequent runs, avoiding
recompilation.  `.skip` markers prevent re-attempting known-unsupported functions.

### Phase 8.1 — Integer locals

When an integer value is stored in a local variable and is used only in integer
operations, it is kept in a C `int` local rather than boxing/unboxing a `JSValue`
on every access.

### Phase 8.2 — Self-recursive integer tail calls

A direct tail call from a function to itself where the accumulator is an integer
is emitted as a C loop rather than a recursive call.

### Phase 8.3 — JIT-to-JIT direct calls

When a JIT-compiled function calls another known JIT-compiled function (detected
at code-generation time via closure variable inspection), a guarded direct C call is
emitted instead of an indirect call through `js_jit_call()`:

```c
if (js_jit_check_and_extract(_f, __jit_f_<callee_hash>, &_dc, &_dv))
    _r = __jit_f_<callee_hash>(ctx, JS_UNDEFINED, N, _ca, _dc, _dv);
else
    _r = _RT->call(ctx, _f, JS_UNDEFINED, N, _ca);
```

When both caller and callee land in the same `combined.so`, GCC can inline the callee.

### Phase 8.4 — Integer arguments

Function arguments whose type is statically known to be integer at all call sites
are kept as C `int` rather than `JSValue` through the function entry preamble.

### Phase 8.5 — Dense array fast path

`get_array_el` and `set_array_el` check whether the object is a dense JS array and
the index is an integer; if so, the element is read/written directly from
`obj->u.array.values[]` without going through the property lookup machinery.

### Phase 8.6 — Float64 typed property slots

When the IC for a `get_field` confirms that the target slot contains a `float64`
value (marked by `ic->kind == 1`), the slot is read directly as a C `double` and
pushed as a typed float64 local, deferring boxing until the value is needed as a
`JSValue`.

### Phase 10 — LTO combined library

See §10.

## 9. Inline Property Cache (IC)

### 9.1 Design

Each `get_field` / `get_field2` / `put_field` opcode compiles a *monomorphic* IC
entry: a `static JSJITICEntry` variable local to the JIT function.

```c
typedef struct {
    void     *shape;   /* JSShape* — NULL = uninitialized, 1 = megamorphic */
    uint32_t  slot;    /* property slot index within the shape's prop[] */
    uint32_t  atom;    /* JSAtom at slot — ABA guard */
    uint8_t   kind;    /* 0=JSValue slot, 1=float64 typed slot */
} JSJITICEntry;
```

The IC check (`JIT_IC_CHECK` macro) verifies:

1. `ic->shape != NULL` and `ic->shape != JIT_IC_MEGAMORPHIC`
2. `JS_VALUE_GET_TAG(obj) == JS_TAG_OBJECT`
3. `obj->shape == ic->shape` (shape pointer identity)
4. `ic->slot < obj->shape->prop_count` (bounds check, ABA guard part 1)
5. `obj->shape->prop[ic->slot].atom == ic->atom` (atom ABA guard)

On a hit, the property is read/written directly at the cached slot index via
`js_jit_ic_read` / `js_jit_ic_write`.

On a miss, the full `JS_GetProperty` / `JS_SetProperty` path is taken, and
`js_jit_ic_fill_get` / `js_jit_ic_fill_put` is called to populate (or invalidate)
the IC entry.

### 9.2 Megamorphic sentinel

If a callsite sees two or more distinct shapes, the IC entry's `shape` field is set
to `JIT_IC_MEGAMORPHIC` (`(void*)1`).  Subsequent calls to `js_jit_ic_fill_*` skip
the `find_own_property` hash lookup and go straight to the slow path, keeping the
miss overhead proportional to a direct slow-path call.

### 9.3 ABA guard

The atom stored at a slot can change if a shape is freed and its memory is reused for
a different shape at the same address.  Storing and verifying the `atom` field detects
this: if the atom differs, the check fails and the slow path re-validates the IC.

### 9.4 Inline expansion

`JIT_IC_CHECK` is a C macro defined in `quickjs-jit.h`.  It uses hardcoded byte
offsets into `JSObject` and `JSShape` to access the relevant fields without requiring
the full internal struct definitions in JIT-generated translation units.  The offsets
are verified at compile time by `_Static_assert` in `quickjs.c`:

```c
_Static_assert(offsetof(JSObject,  shape)      == JIT_OBJIC_SHAPE_OFF,       "...");
_Static_assert(offsetof(JSShape,   prop_count) == JIT_SHAPEIC_PROPCOUNT_OFF, "...");
_Static_assert(offsetof(JSShape,   prop)       == JIT_SHAPEIC_PROP_OFF,      "...");
_Static_assert(sizeof(JSShapeProperty)         == JIT_SHAPEIC_PROPSIZE,      "...");
_Static_assert(offsetof(JSShapeProperty, atom) == JIT_SHAPEIC_ATOM_OFF,      "...");
```

Because the check is a macro, the compiler sees the full guard body at each call
site and can schedule it optimally — no function call overhead.

## 10. Phase 10 — LTO Combined Library

### 10.1 Motivation

When each function compiles to its own `.so`, GCC cannot inline a JIT function
into its callers, propagate constants across function boundaries, or vectorise
loops that span multiple functions.  Phase 10 addresses this.

### 10.2 `--jit-warmup`

Executes the script and compiles every eligible function to both a `.so` and a `.c`
file in the cache.  The `.c` file is the raw generated C source; it is saved
alongside the `.so` for use by the linker step.

### 10.3 `--jit-link`

After execution, collects all `.c` files seen during the run and invokes:

```sh
gcc -O3 -flto -shared -fPIC \
    <hash1>.c <hash2>.c ... \
    __jit_manifest.c          \   # manifest table (hash → func_ptr)
    qjs_ic_<mtime>.o          \   # quickjs.c LTO object (P10.5)
    -o combined.so
```

GCC compiles all 527 (for V8bench) translation units simultaneously under LTO,
enabling cross-function inlining and IPO.

The `__jit_manifest` array in the output:

```c
JSJITManifestEntry __jit_manifest[] = {
    { 0xaabbcc0011223344ULL, __jit_f_aabbcc0011223344 },
    ...
};
int __jit_manifest_count = 527;
```

allows the loader (§10.4) to map hashes to function pointers.

### 10.4 Manifest loader (`--jit-aot` with `combined.so`)

`js_jit_preload_combined()` opens `combined.so` with `dlopen(RTLD_NOW | RTLD_LOCAL)`
and resolves `__jit_manifest` / `__jit_manifest_count`.  The manifest pointer is
cached globally.

In `js_jit_queue_gcc`, if the manifest is loaded and the current function's hash
is found, the `jit_func` pointer is patched immediately from the manifest —
no individual `.so` file is opened.

`js_jit_install_combined_if_exists()` is called once per script file (including
`load()`'d files) to patch any functions that registered their bytecodes after
the initial preload.

### 10.5 IC check inlining (P10.5)

The `JIT_IC_CHECK` macro (§9.4) ensures that the inline cache hot path compiles to
a sequence of comparisons at each call site with no function call overhead.

The LTO object compiled from `quickjs.c` enables GCC to inline other internal
helpers (e.g., `js_jit_ic_read`, array helpers) across the combined.so boundary.

Verification:

```sh
objdump -d ~/.cache/qjs-jit/combined.so | grep -c 'call.*js_jit_ic_check'
# → 0
```

## 11. Eligibility and Limitations

A function is eligible for JIT compilation if all of the following hold:

| Condition | Reason |
|---|---|
| `func_kind == JS_FUNC_NORMAL` | Generators and async functions use `yield`/`await` which require saved interpreter state |
| Not an `eval()` frame | `eval` has dynamic variable scoping incompatible with the JIT's static local model |
| Simple parameters | Destructuring, rest (`...args`), and default parameter expressions require interpreter-level setup |
| No `home_object` | Class methods that use `super` need the home-object mechanism |
| Not a derived class constructor | Derived constructors have special `super()` return-value rules |

Additionally, a function is permanently skipped (`.skip` marker written) if the
code generator encounters any opcode it has not implemented.  These functions always
run in the interpreter.

### Unsupported opcodes (representative)

- `with` statement, `eval` as an opcode, `import()`
- Generator opcodes (`yield`, `await`)
- Some rare iterator protocol opcodes

These have `.skip` markers in the cache and produce no compilation overhead after
the first run.

## 12. Embedding API

The public JIT API is declared in `quickjs-jit.h`.  All symbols are only available
when `CONFIG_JIT` is defined.

### Lifecycle

```c
void js_jit_init(void);         /* called once after JSRuntime creation */
void js_jit_free(void);         /* called before JSRuntime destruction */
```

### AOT compilation

```c
/* Compile all functions reachable from b's closure tree. */
void js_jit_compile_all(JSContext *ctx, JSFunctionBytecode *b);

/* Wait for all pending GCC background jobs to finish. */
void js_jit_drain(void);

/* Enable AOT mode (equivalent to --jit-aot flag). */
void js_jit_set_aot_mode(int active);
```

### Combined library

```c
/* Open combined.so and cache its manifest.  Returns entry count, or -1 on error. */
int js_jit_preload_combined(void);

/* Scan the manifest and install functions whose bytecode is now registered.
 * Call after js_jit_compile_all() + js_jit_drain().  Idempotent per entry. */
int js_jit_install_combined_if_exists(void);
```

### Linking

```c
/* Combine all .c files seen in this run into combined.so (--jit-link).
 * Returns the number of functions combined, or -1 on error. */
int js_jit_link(void);

void js_jit_set_link_mode(int active);
```

### Diagnostics

```c
/* Enable --jit-dump-c: print generated C to stderr. */
void js_jit_set_dump_c_mode(int active);

/* Return 1 if the function has a cached .c source file. */
int js_jit_cache_has_c_src(JSFunctionBytecode *b);
```

### Bytecode accessors (used by quickjs.c)

```c
uint8_t  js_jit_fb_get_tier(JSFunctionBytecode *b);
void     js_jit_fb_set_func(JSFunctionBytecode *b, JSJITFunc f, void *handle, int tier);
int      js_jit_fb_inc_count(JSFunctionBytecode *b);
int      js_jit_is_eligible(JSFunctionBytecode *b);
void     js_jit_free_bytecode(JSFunctionBytecode *b);  /* called when b is freed */
```

## 13. Debugging and Diagnostics

### 13.1 Inspect generated code

```sh
./qjs --jit-dump-c script.js 2>&1 | less
```

Each function is preceded by `/* ==== JIT: <name> [<hash>] ==== */`.

Or retrieve a cached function's source:

```sh
cat ~/.cache/qjs-jit/<hash>.c | less
```

### 13.2 Identify skipped functions

```sh
ls ~/.cache/qjs-jit/*.skip
```

Each `.skip` file corresponds to a function whose code generation failed.  The file
name is the hash; cross-reference with `--jit-dump-c` output or the corresponding

### 13.6 Compile-time structural assertions

`quickjs.c` contains five `_Static_assert` checks that fire at compile time if the
internal struct layout diverges from the byte offsets declared in `quickjs-jit.h`
(used by `JIT_IC_CHECK`).  If a `quickjs.c` struct is refactored, the build will
fail with a clear message such as:

```
quickjs.c: error: static assertion failed: "JIT_OBJIC_SHAPE_OFF mismatch"
```

## 14. Performance Notes

### 14.1 Benchmark environment (V8bench v6, WSL2, Intel x86-64)

| Mode | Score range | Notes |
|---|---:|---|
| Interpreter (no JIT) | 964–1008 | GCC -O2, computed-goto dispatch |
| `--jit-warmup` | ~944 | Individual `.so` per function, `-O2` |
| `--jit-aot` + `combined.so` | 896–1156 | LTO `-O3`, IC inlined, 527 functions |

The wide range in `--jit-aot` scores reflects WSL2 timer variance and whether the
Richards benchmark's shaped-object IC fast-path engages consistently.  In runs where
it does, Richards scores ~3300 vs ~860 for the interpreter (~3.9× speedup).

### 14.2 Where the JIT wins

- **Integer-only hot loops** — arithmetic without allocation, no boxing overhead.
- **Property-access-heavy code** — the IC fast-path reduces `get_field` to ~5
  inline comparisons and a direct slot load, vs a full hash table lookup.
- **Call-heavy code where callees are in `combined.so`** — GCC inlines small helper
  functions across JIT function boundaries when both are compiled together.

### 14.3 Where the JIT is neutral or slower

- **RegExp-heavy code** — the regexp engine is not JIT-compiled; functions that
  consist mostly of regexp calls gain nothing.
- **Functions with unsupported opcodes** — they fall back to the interpreter.
- **Short-lived functions** — a function called fewer than `JIT_THRESHOLD_GCC` times
  (default 100) never gets compiled.  Use `--jit-threshold-gcc=N` with a lower N to
  lower the bar, or `--jit-threshold-gcc=0` for an AOT pre-pass.
- **First run after cache clear** — GCC compilation adds latency proportional to the
  number of hot functions; use `--jit-aot` to front-load this.

### 14.4 Ceiling

The JIT is a JS→C source compiler.  Its practical ceiling is determined by:

- The JSValue boxing ABI (every JS value is a 16-byte tagged union at function
  boundaries).
- The IC miss penalty (slow path through hash table on first access per shape).
- GCC's inability to see the interpreter's inner loop structure.

Approximate ceiling: ~1.5–2.5× the interpreter for typical JS benchmarks.  Numeric
kernels (integer or float64 with no allocation) can exceed this; object-heavy code
stays near the interpreter.
